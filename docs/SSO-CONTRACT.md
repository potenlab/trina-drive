# Trina Cloud SSO and member-sync contract (`tdcloud-sso-v1`)

The wire contract between the **Trina Cloud console** (`cloud/control`, the identity and membership source) and a
**team drive** (`https://<slug>.cloud.trina.app`, this product in cloud mode). Both sides implement against
[`test/fixtures/sso-v1.json`](../test/fixtures/sso-v1.json): its `vectors` are signed assertions with the answer each
must get, `member_sync.vectors` the ordering rules. The fixture is generated by `scripts/gen-sso-fixture.ts`
(deterministic: fixed test keys) and checked by `test/contract-sso-v1.test.ts` against a reference verifier.
To change the contract: change the script and this page in one PR, regenerate, then both sides.

Self-hosted installs are not affected: everything here is active only when the `TDRIVE_CLOUD_*` environment is set.

## Environment of a team drive (written by the console's `teamEnv`)

| Variable | Value |
|---|---|
| `TDRIVE_CLOUD_ISSUER` | `https://cloud.trina.app` (assertion `iss`, exact match) |
| `TDRIVE_CLOUD_TEAM` | the team's `teams.public_id`, `team_` + 20 hex (assertion `aud`, sync `team`) |
| `TDRIVE_CLOUD_SSO_KEYS` | `[{"kid":"k1","x":"<base64url raw Ed25519 public key>"}]`, two entries while rotating |
| `TDRIVE_CLOUD_CALLBACK_TOKEN` | `tdcb_…` (env file / SSM SecureString only; the console keeps its SHA-256) |
| `TDRIVE_CLOUD_CONSOLE_URL` | `https://cloud.trina.app` (links in the drive) |
| `TDRIVE_SSO_ONLY` | `1`: password sign-in answers 409 `use_sso` for people with a `cloud_user`; `/api/setup` 404 |

Keys: Ed25519, private keys in the control database wrapped by the existing `KeyWrapper` (`TDCLOUD_KMS_KEY_ID`,
context `{purpose: 'sso', kid}`). Rotation: add the new public key to every team's env (that needs a `recreate`, the
env is written at (re)start), then sign with the new `kid`, then retire the old one after every team has restarted.

## Sign-in flow

1. **Drive** `GET /api/sso/start?return=/files[&reauth=1]`: makes `state` (base64url of 32 random bytes), stores
   `{sha256(state), return, reauth}` server-side for 10 minutes, sets `__Host-tdrive_sso=<state>` (HttpOnly, Secure,
   SameSite=Lax, Path=/, 600 s; plain-http dev: `tdrive_sso`), and 303s to
   `https://cloud.trina.app/sso/authorize?team=<public_id>&state=<state>[&max_age=0]`.
   `return` is a relative path (`/…`, not `//…`), kept on the drive, never sent to the console.
2. **Console** `GET /sso/authorize`: no session → `/login?next=<relative>`. Not an active member of that team (or no
   such team) → the same 404. `max_age=0` → the password again (and TOTP; owners and admins must have one). The callback
   URL comes from the team record, never from the query.
3. **Console** answers with a page that auto-POSTs (form_post) `assertion` and `state` as
   `application/x-www-form-urlencoded` to `https://<slug>.cloud.trina.app/api/sso/callback`. Console CSP:
   `form-action 'self' https://*.cloud.trina.app`.
4. **Drive** `POST /api/sso/callback` (route registered with `{ raw: true, crossOrigin: true }`: no Origin check; the
   state cookie and the signature prove the request) verifies in this order, answering the first error:

   | # | Check | Error |
   |---|---|---|
   | 1 | state cookie present and equal to the posted `state` (timing-safe) | `bad_state` |
   | 2 | `^v1\.[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+$`, ≤ 4096 bytes, payload a JSON object with every required claim in shape | `malformed` |
   | 3 | `kid` is configured | `unknown_kid` |
   | 4 | Ed25519 signature over ASCII `"tdcloud-sso-v1." + <payload segment>` | `bad_signature` |
   | 5 | `iss` = `TDRIVE_CLOUD_ISSUER` | `bad_issuer` |
   | 6 | `aud` = `TDRIVE_CLOUD_TEAM` | `bad_audience` |
   | 7 | `iat`/`nbf` ≤ now + 60 s; now ≤ `exp` + 60 s; 0 < `exp − iat` ≤ 120 s | `not_yet_valid`, `expired`, `bad_lifetime` |
   | 8 | `state_hash` = base64url(SHA-256(state)) | `bad_state` |
   | 9 | `jti` not in `sso_used` (insert it in the sign-in transaction; prune after `exp` + 60 s) | `replayed` |

   Then: find or create the person (below), revoke the session the browser came with, start a new one, delete the
   stored state, 303 to `return` (default `/#/files`). People with a second factor on the drive (and hosted admins)
   go through `/#/sso-second/<ticket>` first. Errors: 303 `/#/sso-error/<code>`, nothing else shown.
   With `reauth=1` stored and now − `auth_time` ≤ 120 s, the new session counts as a fresh login (`markReauth`).

### Assertion

`v1.` + base64url(UTF-8 JSON claims) + `.` + base64url(64-byte Ed25519 signature). No JSON canonicalization: the
signature covers the payload segment exactly as sent.

```json
{ "iss": "https://cloud.trina.app", "aud": "team_3f2a9c41d07be5a86c19", "kid": "k1",
  "sub": "usr_9a41c2e07d5b3f8e6a10", "email": "mina@trina.app", "name": "Mina Kim", "role": "member",
  "iat": 1761223456, "nbf": 1761223456, "exp": 1761223516, "auth_time": 1761222856,
  "jti": "<base64url 16 bytes>", "state_hash": "<base64url sha256(state)>", "amr": ["pwd"], "sync_seq": 7 }
```

`role`: `owner | admin | member` (owner and admin → drive admin). `amr`: `pwd | link | totp`. `sync_seq`: the newest
member-sync `seq` the console had made for this team when it signed.

### Person on sign-in

`accounts.cloud_user = sub` → else a person with no `cloud_user` and the same email (case-insensitive) → else create
(JIT; `TDRIVE_MAX_PEOPLE` applies). With `applied` = the drive's `meta.cloud_sync_seq`, an assertion is **newer** when
`sync_seq > applied`:

- inactive person: reactivated only by a newer assertion, else refused (`deactivated`) — a pass signed just before a
  removal cannot undo it; reactivation never revives old tokens (they were revoked on deactivation);
- active person: `admin` taken from `role` only from a newer assertion, else the drive keeps its value;
- no person yet: created.

This is the clock-free form of plan 10.2 #5 ("`iat` < last sync applied → do not reactivate").

## Member sync (console → drive)

`driver.exec(host, slug, ['cloud', 'sync-members', '--json', <base64url JSON>])` (the drive also takes `--stdin`).
The console sends the **whole desired state** after every membership change, after provisioning, as the **last step of
wake / restart / recreate** (the team stays paused until it succeeds), and once a day.

```json
{ "version": 2, "team": "team_…", "seq": 8, "at": 1761223500000,
  "members": [
    { "cloud_user": "usr_…", "invite": null, "email": "mina@trina.app", "name": "Mina Kim", "role": "member", "status": "active" },
    { "cloud_user": null, "invite": "inv_000000000017", "email": "jae@partner.example", "name": "", "role": "member", "status": "invited" } ],
  "events": [
    { "id": "evt_…41", "type": "member.removed", "cloud_user": "usr_…", "at": 1761223499000 },
    { "id": "evt_…42", "type": "member.sessions_revoked", "cloud_user": "usr_…", "at": 1761223499500, "reason": "console_password_changed" },
    { "id": "evt_…43", "type": "invite.revoked", "invite": "inv_000000000016", "at": 1761223499800 } ] }
```

- **Order**: `seq` is per team and strictly increasing. The drive applies a payload only when `seq` >
  `meta.cloud_sync_seq` and stores it in the same transaction; otherwise it answers `stale` (exit 0). A retried old job
  can never undo a newer one.
- **Members**: set `cloud_user`, email, display name, `admin` (owner/admin), `active = 1`. Invited people get a row now
  (`accounts.cloud_invite`, no password) so they can be shared with before they sign up; they join Everyone when
  active. The first payload after acceptance carries both `cloud_user` and `invite` to link the row.
- **Removal** (anyone with a `cloud_user` or `cloud_invite` not listed): `active = 0` and every credential cut —
  sessions, personal access tokens, OAuth grants, app passwords.
- **Events** (applied after the members, same transaction, idempotent by `id`): `member.removed` (as above, explicit
  in the audit), `member.sessions_revoked` (web sessions only), `invite.revoked` (deactivate the invited row).
- **Unmanaged**: people with neither `cloud_user` nor `cloud_invite` (CLI, break-glass) are never changed and are
  reported in `unmanaged` so the console can warn.
- **Everyone** is a system group in cloud mode = exactly the active members; the drive's people/group/admin APIs answer
  409 `managed_by_console` under `TDRIVE_SSO_ONLY`.
- A person who **becomes admin** here: notice to every other admin and to them, and an audit row.

Output (one JSON line): `{"ok":true,"applied":true,"seq":8,"created":1,"updated":0,"deactivated":1,"reactivated":0,"people":3,"unmanaged":[…]}`,
or `{"ok":true,"applied":false,"seq":8,"current_seq":9,"reason":"stale"}`, or exit 1 with
`{"ok":false,"error":"bad_version|wrong_team|bad_json|people_limit"}` — the console then retries with backoff until it
succeeds and shows a pending removal in red.

## Invite from the drive (drive → console)

`POST https://cloud.trina.app/api/team-callback/invites`, `Authorization: Bearer <TDRIVE_CLOUD_CALLBACK_TOKEN>`,
`{"email":"…","role":"member","by_cloud_user":"usr_…"}` → 201 `{"status":"invited","invite":"inv_…"}`. Only `member`
(400 `bad_role`); `by_cloud_user` must be an active console admin/owner of the team now (403 `not_admin`); 50 per team
per day (429). The console creates or reuses the open invite, mails it and queues a sync. Accepting an invite requires
the signed-in console account's confirmed email to equal the invited email.

## Usage (console ← drive)

`driver.exec(host, slug, ['cloud', 'usage', '--json'])` hourly:
`{"people":7,"ai_people_30d":4,"files_bytes":…,"trash_bytes":…,"versions_bytes":…,"quota_bytes":…,"last_activity_at":…}`.
